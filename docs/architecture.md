# 技术架构基线

## 1. 架构目标与约束

当前仓库只有产品说明文档，没有源码、团队规模、流量数据或已确定的外部接口。因此这是可调整的架构基线，不是已经实施的设计。首要目标是：可靠地支持一个端到端试点、保证组织数据隔离和操作可追溯，并保持低成本迭代。

## 2. 演进策略

首版优先采用**模块化单体**：一个部署单元，内部按领域划分模块，模块间通过明确接口交互。数据库按领域组织表和权限边界。只有当独立扩缩容、独立发布、团队所有权或故障隔离需求得到真实证据支持时，再拆分服务。

候选应用边界：

- **身份与组织**：用户、组织、成员、角色、授权。
- **任务协同**：任务、状态流转、责任人、检查项、附件和交付。
- **资源管理**：设备及其档案、状态、维护记录。
- **事件与通知**：异常/事件、处理人、状态和通知偏好。
- **审计与导出**：重要操作记录、查询和受控数据导出。
- **集成适配**：地图、客户系统和设备数据源的边界；每个连接器需单独授权与审查。

具体语言、框架、数据库、地图供应商和部署平台，待确定首发端形态、团队能力、地区要求和集成约束后选定。

## 3. 逻辑组件

```text
Web / Mobile 客户端
        │ HTTPS（身份认证、租户上下文、授权检查）
        ▼
应用 API ── 身份与组织 ── 任务协同 ── 资源管理
   │              │             │              │
   ├──────────────┴─────────────┴──────────────┤
   │         关系型业务数据 + 审计记录           │
   ├── 附件对象存储（私有、短期签名访问）         │
   └── 外部适配器（地图 / 客户系统 / 数据源）      │
```

首版可以采用单一应用与托管基础设施。不要因图中逻辑模块而提前部署多套服务。

## 4. 核心领域对象（候选）

- `Organization`：客户/运营组织边界。
- `Membership` / `Role`：用户属于组织的关系及权限。
- `Mission`：任务目标、状态、时间窗口、空间描述、责任方和交付要求。
- `MissionAssignment`���任务与人员、设备或服务方的分配关系。
- `ChecklistItem`：任务准备/执行检查项、完成状态和确认信息。
- `Asset`：设备档案与状态；初版不保证来自实时设备遥测。
- `Event`：异常或事件、来源、严重度、负责人、处理记录。
- `Attachment` / `Deliverable`：私有文件及交付元数据。
- `AuditRecord`：操作者、组织、动作、对象、时间及必要的变更摘要。

业务对象应有稳定标识、创建/更新时间和组织归属。状态变更应通过受控业务操作进行，而不是让客户端任意改写状态字段。

## 5. 安全、隐私与可靠性底线

- **认证与授权**：使用成熟身份方案；关键 API 服务端校验用户身份、组织成员关系和对象级权限，不信任客户端传入的组织 ID。
- **租户隔离**：所有业务查询和后台任务都显式应用租户边界；对跨租户访问做自动化负向测试。
- **最小权限**：按角色授予所需操作；管理员操作、导出和权限变更写入审计。
- **文件保护**：附件默认私有；上传校验大小和类型；下载采用短时授权；避免公开桶和永久可猜测链接。
- **凭证管理**：密钥不提交到仓库；按环境隔离，支持轮换；日志不得包含密码、令牌或不必要的个人信息。
- **数据治理**：确定数据分类、保存期限、删除/导出流程及备份恢复策略后再上线真实客户数据。
- **安全相关信息**：显示权威来源、更新时间和适用范围；信息不可用或过期时明确呈现，不宣称平台自动批准飞行或保障飞行安全。
- **运营韧性**：健康检查、错误监控、备份恢复演练；上线前定义可接受的恢复时间和数据丢失目标。

## 6. API 与集成原则

- 优先设计版本化、可审计的业务 API；先服务产品自身，外部开放 API 需有身份、配额和权限策略。
- 集成使用适配器隔离外部协议差异；记录数据来源、更新时间、失败状态和重试结果。
- 对外数据交换采用最小字段集、明确用途和租户授权；幂等处理重复请求。
- 地图、气象、设备或监管相关数据不可被假设为实时、完整或权威；界面需表明其来源和时效。
- 任何涉及飞行器控制或安全关键执行的集成，都必须经过设备厂商授权、风险评估、适用认证与专门安全验证；不属于当前蓝图的首版范围。

## 7. 质量与交付

在代码启动前确定并自动化最低检查：格式/静态检查、单元测试、API 契约测试、权限与租户隔离测试、关键流程端到端测试、依赖漏洞检查和构建验证。数据库迁移需可审查、可回滚或有明确恢复方案；发布需区分开发、测试和生产环境。

建议按风险优先级测试：跨租户数据泄漏、无权审批/导出、非法状态流转、附件越权、重复提交、通知失败以及外部数据过期。

## 8. 何时调整架构

只有出现可观察的瓶颈或组织需求再升级：

- 持续增长的遥测/事件吞吐需要独立流式处理。
- 特定领域需要独立扩缩容、独立发布或故障隔离。
- 多团队需要明确服务所有权和独立交付。
- 数据保留、区域部署或法规要求需要独立存储边界。

在这些证据出现前，保持简单、可测、易迁移。
